## 自查清单：不知道做什么时，按顺序问这 5 个问题

1. **有没有用户（包括你自己）在实际使用中抱怨或卡住的地方？** → 有就修，这是最高优先级信号（上次的断网丢成绩 bug 就来自这条）。
2. **有没有数据丢失 / 写错 / 串号的风险点？** → 数据安全永远优先于新功能。
3. **CI 或本地测试有没有红？** → 先修，不许带病上路。
4. **有没有被 YAGNI 挡住、但真实想加的功能？** → 想清楚「什么信号出现才值得做」，写进下方黄区，等信号。
5. **以上都没有？** → 这就是完成状态。去打 tag、写文档、整理 README 截图，或干脆休息。**不要为了「感觉该做点什么」而发明需求。**

## 刻意的取舍（做了会后悔的事）

- **不引** TypeScript / Pinia / ORM / UI 组件库——specs YAGNI 章节是硬约束
- **不做** 公网部署、跨设备多端同步、排行榜社交化（段位/每日挑战）——定位是局域网注意力训练工具，复杂度天花板不值得捅破
- **不追** 100% 覆盖率——97.7% 已够，价值盲区优先于数字

以上取舍只有在「被真实使用场景逼到」时才重议，且必须先在 specs 里改设计文档，不允许顺手破例。
